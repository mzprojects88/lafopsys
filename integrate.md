# DATA/ → lafopsys Integration Plan

## Context

`C:\Users\ADMIN\Desktop\Sir Butch\littlearkfoundation\DATA\` is the foundation's real operational data — nine spreadsheets, two PDF reports, and a pre-cleaned `clean/*.json` layer, none of it in git. Only a fraction of it has ever been wired into lafopsys: `patients.json`, `carers.json`, `donors.json`, and `donations.json` (in-kind only) sync in automatically via `scripts/sync-real-data.mjs`. Everything else — cash donations, the bank ledger, expenses/reimbursements, the DSWD government caseload report, the calendar, the Care Cart/occupancy logs, the 248-sheet daily bed tracker, and both PDF annexes — has never been touched.

The point of this plan is to close that gap: for every real dataset in `DATA/`, say where it lives today, where it should live in lafopsys (which TypeScript type, which module, which role), and whether it should be a one-time import, an ongoing sync, or something the app itself should generate going forward so the spreadsheets stop being the source of truth at all.

**The good news, confirmed by reading the code, not assumed:** lafopsys's type system was already built anticipating almost all of this. `lib/types/finance.ts` has `CashEntry` with a `cash_donation` source and an `approvalStatus`. `lib/types/house-ops.ts` has `Trip`, `MealService`, `CareCartLog`, `ActivitySession`, `CensusSnapshot`, `Room`/`Unit`/`BedPosition`. `lib/types/reports.ts` has a `DSWD` report category and a `MetricSnapshot` shape (`bedNights, meals, trips, careCartMeals, activityParticipants, donationsYtd`) that is almost a field-for-field match to the `Summary YTD` sheet. `Donation.kind` already supports `"cash"`, and `Donor.type` already has `"government"`/`"anonymous"`. None of these currently read real data — `lib/mock-data/{finance,house-ops,reports}.ts` are 100% `makeRng()`-seeded random data. This is a wiring problem, not a design problem, for most of what follows.

**Recommendation:** extend `Patient` with the DSWD fields (they're needed either way for `ReportDefinition` category `"DSWD"`, which already exists as a stub in `reports.ts` with zero real data behind it) rather than modeling this as a separate entity — it's the same 170 people, just more fields per person. `PRIORITY STATUS`/`MSS STATUS`/`PT NAVIGATOR` map more naturally onto `Referral` (the intake pipeline that already exists in `patient.ts` for the partner-hospital portal) as an approval-workflow extension.

**Consumers:** Patients module (social_worker — the intake/case-management fields), Reports module (DSWD Caseload Inventory report, currently a stub with `lastGeneratedAt` but no generator).

### New: Occupancy — `LAF Occupancy Tracker.xlsx` (248 daily sheets)
One sheet per day, Jan 2025–Aug 2026, each a fixed 14-slot roster template (mostly empty — usually 1-2 rows filled per day). This is the real source for `house-ops.ts`'s `Stay`/`CensusSnapshot`, currently pure mock.

**Confirmed parsing hazards** (don't build a naive parser):
- Sheet-name date format changes twice across the range: `MMDDYYYY` (recent), `MMDDYY` (most of 2025), `M/DYY` with no leading zero (early Dec 2025) — needs length-based branching, not one regex.
- Leading whitespace on some sheet names (`" 08062026"`) — must `.trim()` before parsing.
- Sheets are not in strict chronological order (some out-of-sequence inserts) — never infer date from position.
- Column schema itself changed at least once: older sheets (`Count, Patients Name, Birthday, Carers Name, Birthday, Relationship`) vs. newer (`#, Patient's Name, Carer's Name, Relationship to Patient, Next Appointment, Treatment, Address`) — needs schema versioning by date cutover, not one fixed header map.

**Recommendation:** this is exactly what `Stay` (patient/bed/check-in-out) and `CensusSnapshot` (daily rollup) already model — a one-time backfill script producing historical `Stay` records makes sense, but **going forward the app should generate `CensusSnapshot`/`Stay` rows itself from the House Ops check-in/check-out flow that already exists in the module**, not keep reading a spreadsheet. This is the clearest "replace the spreadsheet" case in the whole dataset.

**Consumers:** House-ops module (house_staff, driver), Reports (bed-nights figures feeding `MetricSnapshot`/Annex G accomplishment report).

### New: Scheduling — `LAF Master Calendar 2026.xlsx`
7 sheets. Only the `2026` sheet (458 rows: date, time, event, venue, officer on duty, staff needed, booked by, contact, remarks) is a normalized event log suitable for direct import — `March/April/May 2026` are visual calendar grids (day-number + embedded, sometimes multi-line, event text per cell) needing a bespoke grid parser, and `Sheet9`/`Sheet7`/`For Posting Needs` are small ad hoc scratch sheets not worth importing.

**Recommendation:** map the `2026` sheet onto a new lightweight `Event`/`Booking` type (no existing lafopsys equivalent — closest is `Trip`, which is transport-specific, not general venue booking). Treat the calendar-grid monthly sheets as a one-time historical backfill at most; going forward, this should be an in-app scheduling feature, not a spreadsheet.

**Consumers:** House-ops/Programs module (whoever books Care Cart visits, family events), driver (staff-needed field overlaps `Trip`).

Supersedes the older `LAF PROGRAMS 2026.xlsx` that `DATA/clean/*.json` was built from. Sheet diff confirmed: dropped `DonorsVisitors Information` (donor/visitor counts moved into `Summary YTD`'s `DONORS AND VISITORS` column group instead), gained `Website Dashboard`, `CAF`, `JULY/AUG 2026`.

## Recommended build order

1. **Finance — done.** `scripts/clean-finance-data.py` (new, mirrors `clean-real-data.py`'s pattern) reads `CASH`, `BDO_CASH DONATIONS`, `Bank Statement`, and `Butch reimburments ` and writes `DATA/clean/cash-entries.json` (816 records) + `DATA/clean/finance-import-report.md`. Wired into `sync-real-data.mjs`'s `FILES` list; `lib/mock-data/finance.ts` now does `realCashEntries.length > 0 ? real : mockCashEntries`, same pattern as `patients.ts`/`donors.ts`. `CashEntry` (`lib/types/finance.ts`) gained optional `donorName`, `sourceSheet`, `needsReview`, `reviewReason`, `duplicateOfId`.
   - Per user decision: `CASH`/`BDO_CASH DONATIONS` are auto-merged on exact date+amount+normalized-donor-name match (77 merged); a date+amount collision with a *different*-looking name is kept as two entries, both flagged `needsReview` and cross-linked via `duplicateOfId` (28 pairs) rather than guessed. `Bank Statement` rows are keyword-classified into a `CashEntrySource`; anything that doesn't hit a keyword (277 of 298 rows — most of the feed) is flagged `needsReview` with a default guess rather than presented as confident.
   - **Caught in verification, worth remembering for the next dataset:** `approvalStatus` and `needsReview` are different concepts and must not be conflated. The Approvals page (`app/(app)/finance/approvals`) and the dashboard's "Pending Approvals" KPI both key off `approvalStatus === "pending"` for a *threshold-approval* workflow; the first version of this script set `approvalStatus: "pending"` for every `needsReview` row, which would have dumped 409 historical transactions into that queue. Fixed by keeping `approvalStatus` always `"approved"` for real historical data (it already happened) and leaving `needsReview`/`reviewReason` as the separate data-quality signal. No review UI was built for `needsReview` yet — it's currently only visible in `finance-import-report.md` and the raw data; a review queue is a natural follow-up, not built now to avoid scope creep.
   - Verified: `npx tsc --noEmit`, `npx eslint .`, `npm run build` all clean; every `/finance/*` route still prerenders.
   - **Follow-up fix during Step 3's YTD math**: found 2 rows with genuinely corrupt source dates (a `CASH` cell literally containing the text `"210/2026"`, and another typed as year `3036` instead of `2026`) that had been silently passed through as their raw/garbage value. Added a `date_is_suspect()` check (implausible year or unparseable string) applied to every date field in the script — never guess-corrects, just flags `needsReview` with the reason so a human fixes it at the source. Also surfaced 21 `Butch reimburments` rows with a genuinely blank date cell, now flagged the same way instead of silently passing through as `null`.
2. **Patient DSWD fields — done.** `scripts/clean-dswd-data.py` (new) reads `Patient Database_NCH.xlsx`'s `Copy of For DSWD Caseload Inven` sheet and joins it onto the existing `DATA/clean/patients.json` by normalized name — an *enrichment* join, not a new patient source: an unmatched DSWD row is skipped and logged, never used to mint a new `Patient`. Writes `DATA/clean/patients-dswd-delta.json` (146 records) + `dswd-import-report.md`. `Patient` (`lib/types/patient.ts`) gained 10 optional fields (`religion`, `sectorCaseCategory`, `placeOfBirth`, `illnessType`, `sourceOfReferralText`, `reasonForReferral`, `socialProfileOfParent`, `servicesReceived`, `deathInfo`, `lengthOfStay`); `lib/mock-data/patients.ts` merges the delta in by `patientId`.
   - Match rate: 146/147 exact normalized-name matches, 1 skipped (no matching patient — logged in the report, not guessed).
   - **Known source gap, not a bug:** `religion` is blank for every one of the 146 matched rows — the DSWD sheet's own Religion column is unpopulated in the source. A separate `Religion` sheet (49 rows, Google Form export) has real data but no shared key; a name-only join wasn't done this pass. Documented in `dswd-import-report.md` rather than silently left mysterious.
   - Surfaced on the patient detail page (`app/(app)/patients/[patientId]/page.tsx`) as new `InfoTile`s: Religion and Length of Stay are shown to all roles (administrative, low-sensitivity); Sector/Case Category, Source of Referral, Services Received, and Death Info are gated behind the same `canSeeClinical` check the existing Diagnosis field already uses (29 patients have `deathInfo` populated).
   - Added a `DSWD Caseload Inventory Report` entry to `reportDefinitions` (`lib/mock-data/reports.ts`) with no `lastGeneratedAt` — its underlying data is now real, but no export was actually produced, so it isn't fabricated as "generated." **Did not build an actual report/PDF generator** — the existing "Generate" button on every report in `/reports` is already a `toast (demo)` stub app-wide; building real document generation is a distinct feature, not a data-integration task, and was left alone to avoid scope creep.
   - Verified: `npx tsc --noEmit`, `npx eslint .`, `npm run build` all clean; confirmed the partner-hospital portal (`app/partners/patients/[patientId]`) references none of the new fields, so nothing sensitive leaks to that external-facing view.
3. **Program metrics — done.** `scripts/clean-program-metrics.py` (new) reads `Summary YTD`'s 2-row-header monthly table and writes `DATA/clean/metric-snapshots.json` + `program-metrics-report.md`. Wired into `sync-real-data.mjs`; `lib/mock-data/reports.ts` now does `realMetricSnapshots.length > 0 ? real : mockMetricSnapshots`.
   - Only **6 of 12 months** (Jan–Jun 2026) are actually populated in the source sheet — July–December are blank, not zero-filled or estimated. **Cross-check confirmed the extraction is correct**: the imported `bedNights` sum (2951) exactly matches the sheet's own "TOTAL" row, and the sheet's separate 2025 annual bed-nights figure (2920) matches `LAF-Annex-G-Accomplishment-Report-2025.pdf`'s reported total independently.
   - `donationsYtd` has no source column in this sheet (its "DONORS AND VISITORS" group is donor headcounts, not pesos) — computed instead as a running 2026 cumulative sum from the real `cash-entries.json` + `donations.json` built in Steps 1–2. It deliberately **excludes** the ~56 CASH/BDO_CASH DONATIONS entries flagged `needsReview` in Step 1, so it's a conservative figure that can only go up once those are reconciled, never down.
   - 2024/2025 annual rows are NOT imported as `MetricSnapshot`s — the sheet only gives an annual bed-nights total for those years with no per-metric breakdown, and fabricating zeros for the missing metrics would misrepresent those years as inactive.
   - **Caught in verification**: `app/(app)/analytics/page.tsx` had a pre-existing `monthlyBurn = totalOut / 7 // sample period ≈ 7 months` — a hardcoded constant sized for the old 7-month-ish mock data. With real `cashEntries` now spanning real (and occasionally malformed) dates, this would have silently produced a wrong "Runway" KPI for Finance/Board. Fixed to divide by the actual count of distinct months present in valid-dated outflow entries instead of a magic number.
   - Verified: `npx tsc --noEmit`, `npx eslint .`, `npm run build` all clean.
4. **Care Cart — done.** `scripts/clean-care-cart-data.py` (new) confirmed the sheet really is 3 independent, non-row-aligned tables sharing one sheet (a day-log with a different date range than either of the two food-distribution ledgers) and split them accordingly. Writes `DATA/clean/meal-services.json` (82 records) + `care-cart-logs.json` (46 records) + `care-cart-report.md`. Wired into `sync-real-data.mjs`; `lib/mock-data/house-ops.ts` does the usual `real.length > 0 ? real : mock` for both.
   - **Type changes (additive/loosening only):** `MealService.costPerHead` and `CareCartLog.source` both went from required to optional — neither has a source column in the real sheet, and both UI consumers (`house-ops/meals`, `house-ops/care-cart`) were updated to show "—"/"Unknown" instead of assuming a value. `CareCartLog.timeSlot` gained a new literal `"10:00 & 14:00"` because the food-distribution ledger's own header names a combined window rather than splitting rows per slot — guessing a single slot per row would have misrepresented data the source itself doesn't distinguish.
   - **`ActivitySession` deliberately NOT imported this pass** — the sheet has participant/volunteer counts but no session title and no single facilitator (only a free-text multi-name list), and both are required fields on the type. Fabricating a title or overloading `facilitator` with a name list would have been worse than leaving it as mock data; documented as a gap in `care-cart-report.md` rather than forced through.
   - **Also left out, documented as a future unlock**: the day-log's own per-time-slot Care Cart headcount columns (10:00/12:00/14:00/17:00, ~83 rows) have real numbers but no item-description text, so they can't become `CareCartLog` records until `itemsServed` is made optional too — a candidate for a later pass, not done now.
   - Duplicate same-day submissions in the day-log (10 dates had 2 rows, a Google-Form resubmission pattern) were resolved by keeping the latest by Timestamp, not summed or arbitrarily picked — documented in the report.
   - Verified: `npx tsc --noEmit`, `npx eslint .`, `npm run build` all clean; both consumer pages already use the paginated `DataTable` component, so no unbounded-list risk at real-data scale this time.
5. **Occupancy — done, scoped to `CensusSnapshot` only.** `scripts/clean-occupancy-data.py` (new) parses all 248 daily sheets and writes `DATA/clean/census-history.json` (248 real daily headcounts, 2025-01-23 to 2026-08-11) + `occupancy-report.md`. Wired into `sync-real-data.mjs`; `lib/mock-data/house-ops.ts` does `real.length > 0 ? real : mock`, **truncated to `<= TODAY_ISO`** so `censusHistory[length-1]` keeps meaning "today" for the dashboard/house-ops pages that assume that (the source range extends a few days past the app's fixed demo-today constant).
   - **Both structural risks flagged before coding were verified empirically, not assumed**: all 248 sheet names parse unambiguously by digit-length (8/6/5) with zero duplicate dates — no cutover-date table needed; and the roster really is a full daily census (the same patient recurs on consecutive sheets while in-house), confirming a per-day headcount is meaningful. The 28 distinct header layouts are handled by searching each sheet's own header row for "patient...name"/"carer...name"/"relationship" labels rather than hardcoding column positions per era.
   - **`Stay` (bed-level check-in/check-out history) was deliberately NOT generated from this data** — the roster has no bed/unit column at all, only names, and `Stay.bedPositionId` is required and read by the floor-plan board, house-occupancy-summary, and the partner portal's bed map to determine which specific bed is occupied. A fabricated/round-robin bed assignment would make those views look precise while being wrong; leaving it undefined would render every bed empty, including for patients really admitted today — a worse regression than not touching `Stay`. `lib/mock-data/patients.ts`'s existing `stays` generator is untouched.
   - **Type change**: `CensusSnapshot.unitsOccupied`/`unitsShared` went from required to optional (no bed-level detail in the source, only total headcount). Fixed 2 KPI tiles each on the Analytics and House-ops dashboards that would otherwise have computed `NaN%`/`undefined / 13` for real days.
   - **Caught a second-order bug while verifying**: `finance/cost-per-outcome` divides program spend by `bedNights` (now real and non-zero via `censusHistory`), but real `cashEntries` have no `programId` at all (documented gap from Step 1) — so `programSpend()` always returns 0, and the page would have silently shown **"₱0.00 cost per bed night"** (implying nothing was spent) instead of "—" (unknown). Fixed by gating all four KPIs on whether any `cashEntries` actually carry program attribution.
   - **Also fixed**: the dashboard's "Patients & Admissions Trend" card is explicitly labeled "Last 30 days" but fed the *entire* `censusHistory` array — harmless with 30 mock days, but real data spans ~217 truncated days, which would have both broken the chart's own label and crowded the X-axis. Windowed to `.slice(-30)` to match what the label actually promises.
   - Verified: `npx tsc --noEmit`, `npx eslint .`, `npm run build` all clean.
6. **Calendar — done.** `scripts/clean-calendar-data.py` (new) reads only the `2026` sheet's normalized event log (the other 6 sheets — 3 visual calendar grids + 3 scratch sheets — were confirmed not worth a second, bespoke parser, per the original scoping) and writes `DATA/clean/calendar-events.json` (237 records) + `calendar-report.md`. Wired into `sync-real-data.mjs`.
   - No existing type fit (`Trip` is transport-specific) — added a new `CalendarEvent` type (`lib/types/calendar.ts`) and `lib/mock-data/calendar.ts`. No mock fallback generator exists for this one (it's a genuinely new dataset, not a mock-to-real swap) — an empty array when `DATA/` isn't present is the honest "no data" state, same as `patients.ts`/`donors.ts`.
   - The sheet only writes a date on the first event of a day — 89 of 237 records had their date forward-filled from the prior row rather than treated as missing.
   - **No UI page was built to browse these events.** Confirmed no calendar/scheduling module exists anywhere in the app to attach this to — building one is a feature request, not a data-integration task, so the data + type + pipeline are ready for whenever that's requested, matching how ActivitySession and report-PDF-generation were left similarly unbuilt in earlier steps.
   - Verified: `npx tsc --noEmit`, `npx eslint .`, `npm run build` all clean.

**All 6 steps of the integration plan are now complete.**

Each step follows the same two-script shape already established: a heavier, manually-run Python/Node extraction step (mirroring `scripts/clean-real-data.py`) writing to `DATA/clean/*.json`, and the lightweight `sync-real-data.mjs` (already wired into `predev`/`prebuild`, already `[]`-safe when `DATA/` is absent) picking it up — no new infrastructure pattern needs to be invented.
